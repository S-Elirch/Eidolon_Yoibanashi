# Eidolon Yoibanashi · 夜间搭话模块：接入与扩展

作者：[S-Elirch](https://github.com/S-Elirch) · [仓库](https://github.com/S-Elirch/Eidolon_Yoibanashi)。

本模块为进入聊天页面后的主动搭话提供独立生成流程与任务管理，属于需要宿主接线的**嵌入式模块**，不是可直接安装的通用插件。

发布源码以 Eidolon-SC v0.2.0 为基线。模块不导入、调用或修改 `ConversationEngine`；`engine.py` 保持 v0.2.0 原版。普通回复及原有后台搭话继续使用上游流程。

体验与启用方式见[仓库首页](../../../../README.md)，设计与取舍见 [FORK.md](../../../../FORK.md)。本页主要供其他 Fork 的开发者接入和调整。

## 文件职责

| 文件 | 职责 |
|---|---|
| `context.py` | 异步读取历史、记忆、关系与当前情境；提供 `LegacyContext`、`V020Context` |
| `history.py` | 从上游 v0.2.0 移入的历史、礼物和事件叙述函数，沿用仓库 AGPL 许可 |
| `prompt.py` | 是否开口、话题式与偶遇式、关系与事实边界的提示规则 |
| `generator.py` | 组装上下文、申请模型、解析日中双语流与安静结果，释放模型资源 |
| `policy.py` | 夜间资格、关系概率、等待档位、时间曲线及日程决策类型 |
| `host.py` | 异步读取关系与近期交流、检查通话和普通回复状态、保存搭话 |
| `repository.py` | 机会与任务的持久化、去重、计数及清理 |
| `service.py` | 后端任务生命周期、超时、让出机会、流式事件及恢复 |
| `runtime.py` | v0.2.0 宿主接线、账户模式、活动记录和 HTTP 路由 |

## 当前规则

- 默认关闭；按账户资料时区，于 22:00–次日 05:00 判断新机会。
- **自然偶遇**：亲密、亲近、信任的机会概率分别为 85%、70%、50%，更低关系不触发。未提供关系状态时，沿用不按关系抽选的宿主兼容路径。
- 自然模式保留 30 分钟近期交流避让、未回应避让；每角色每晚一次准备，同账户每晚最多三次准备。限制的是尝试，不是成功消息数。
- **今晚想听你先说**：整夜有效，05:00 后恢复自然模式；固定选快档，默认 5–8 秒。跳过机会抽取、近期交流与自然模式准备上限；保留关系、忙碌、未回应及已接入的日程限制。同账户只允许一个活动准备任务。
- 今晚模式同一次联系复用已有尝试；刷新、切换模式不会重新生成。用户之后产生新的联系记录，才可能获得下一次尝试。完成一次不会消耗整夜设置。
- 自然模式由模型选择话题式、偶遇式或 `<silent/>`。最近两次成功开场同类时，提示优先考虑另一类，不强制轮换。今晚模式没有旧话题时，提示采用轻量开场。

关系机会与等待抽选是两件事：抽中机会不保证模型一定开口，等待较短也不提高机会概率。

## 生成、展示与保存

前端检测页面可见及连续停留，先查询等待时间；等待结束才请求创建或恢复任务。等待期间离开会取消前端计时，不请求搭话模型。草稿本身不取消准备；用户实际发送消息时，尚未展示的任务让出交流机会。

任务由后端管理，页面通过流式连接接收转圈、正文增量和完成通知。断开页面只结束这个连接，不等于停止后台任务。

- **实际请求模型后**，即使转圈前离开，也不等待页面返回才生成、展示或保存；仍执行用户先发言、通话、会话变化、模型安静和超时等检查。这是为减少已调用模型却仅因离开页面丢弃结果所作的取舍。
- 默认首段最早在准备开始后 4 秒出现，转圈提前量为 2 秒。模型较慢时会更晚；没有增量内容时，不会单靠定时器提前转圈。
- 正文随模型解析增量流式展示，不按假模型固定速度输出。转圈后沿用宿主回复期间暂不能发送的行为，草稿可以保留。
- 实际搭话生成请求采用 120 秒超时，从请求模型时开始；记忆检索不包含在这段计时内。
- 时间戳采用后端开始转圈的时刻，离线时也使用该时刻，不改为返回时间。保存后重新进入直接读取。
- 05:00 后不再开启新机会或首次正文；已开始输出的任务可继续完成并恢复显示。
- 同一机会复用已有任务，避免刷新重复调用。服务重启将未完成任务标记为中断，不自动重试模型。

## 宿主如何接线

在 `assembly.build()` 中、宿主服务就绪后创建一次服务：

```python
from eidolon.visit_outreach.runtime import build_visits

visits = build_visits(backend)
```

默认 `V020Context` 额外读取 v0.2.0 日程与日历上下文，在关系快照前读取日程，以处理已完成日程可能结算的亲密度。**把日程提供给模型，不等于实现角色忙闲避让。**

不具备该版本日程接口的异步宿主，可选择通用上下文：

```python
from eidolon.visit_outreach.context import LegacyContext
from eidolon.visit_outreach.runtime import build_visits

visits = build_visits(backend, context_factory=LegacyContext)
```

这只是上下文选择，不能代替完整移植。还需配套以下接线：

1. `app.py` 调用 `runtime.install(app, backend)` 注册模式、等待查询和流式路由，不重复创建服务；普通消息入口保留活动搭话的忙碌检查。
2. 账户 API 返回开关与模式；删除账户时清理活动任务。`database.py` 的账户数据删除清单包含相关表。
3. `Store.add_reach_out` 保留可选 `created_at` 参数；关闭服务时先结束搭话任务，再关闭数据库。
4. 前端合并账户类型、设置页、`useVisitOutreach`、`LiveConversation` 和消息展示改动。仅复制后端目录不会出现访问触发与转圈界面。

即使用户关闭功能，服务仍应完成初始化。`Backend.visits` 未接线时会明确报错；不要以宽泛异常捕获隐藏缺失的宿主接口。

`EidolonHost` 必须提供异步 `Database`；可选 `relationship_lookup` 为可等待回调，可返回无关系状态。`eligibility` 返回 `(reason, current, relationship)`，非空原因阻止新机会，可由适配方扩展原因。

## 可调整的接口

### 等待范围与时间概率

默认快、中、慢范围分别是 5–8、10–12、15–18 秒；22:00 分档概率为 40/60/0，03:00 为 20/40/40，05:00 边界为 0/0/100，节点间线性插值。

```python
from eidolon.visit_outreach.policy import WaitProfile

visits.wait_profile = WaitProfile(
    ranges=((4, 7), (8, 11), (12, 16)),
    anchors=((22, (40, 60, 0)), (27, (20, 40, 40)), (29, (0, 0, 100))),
)
```

27 表示次日 03:00，29 表示次日 05:00。三档范围都须提供，端点须为 0–3600 秒内的有限值且下限不大于上限；时间节点递增且在一个周期内，各节点概率合计 100。

同用户、角色与机会周期使用稳定抽选值；时间变化调整分档阈值，不重新掷骰，档内相对位置也固定。一次查询后，前端等待不会中途变档；重新进入才按当前时间查询，已有任务优先恢复。今晚模式固定选快档，也会使用配置后的快档范围。

### 日程忙闲与等待覆盖

```python
from eidolon.visit_outreach.policy import ScheduleDecision

def schedule(conversation, local_now):
    # 同步读取接入方已准备好的日程状态，不在此处请求 LLM。
    return ScheduleDecision(
        allowed=True,  # False：搁置新机会
        probabilities=(60, 35, 5),
        ranges=((3, 6), (7, 10), (12, 15)),  # 可省略，沿用 wait_profile
        # draw_key='after-work',  # 仅需重抽等待时提供稳定阶段标识
    )

visits.schedule = schedule
```

该回调是**同步接口**。异步日程服务应先准备可同步读取的状态；搁置新机会不承诺取消已经输出的消息。概率覆盖默认时间曲线，不额外叠加一次关系抽选。未接入时默认允许，不会自动根据角色睡眠、洗澡或忙闲状态避让。

### 上下文与生成器

自定义适配器可通过 `context_factory` 注入，遵循 `context.py` 的异步 `prepare` 和 `VisitContext` 数据契约。版本专用日历导入仅放在 `V020Context` 中。

`VisitService.real_generate` 遵循 `service.py` 的 `Generate` 契约：接收会话、可等待的段落增量回调、可等待的请求通知回调，返回 `list[Segment]`，空列表表示安静。请求模型前必须等待请求通知回调，以复查资格并启动超时；任务启动时捕获生成器，不因刷新重新请求。

### 扩展到白天或任意时段

等待策略与资格时段独立。修改概率曲线不会开放白天；还需协调 `policy.py` 的 `eligibility`、`night_key`、`first_body_deadline`，以及今晚模式周期与前端说明。目前没有统一的任意时段配置接口。

## 兼容性边界

已在 Hibi `my-features` 提交 `1fb2454` 上，通过独立适配与前端合并验证真实模型基础交互。该验证使用通用历史、记忆与基础关系上下文，没有接入 Hibi 专属日程上下文与状态避让，不代表可直接安装或兼容所有版本。

宿主升级应检查账户、异步存储、流式事件和组装接口；也需核对 `history.py` 中移入的历史、照片与礼物格式是否与宿主保持一致。

## 数据兼容性

为兼容已有数据，保留 `dev2_night_tasks`、`dev2_night_opportunities` 表名及历史 `invitation` 列。整夜模式不消费邀请令牌；更名或删除需要数据库迁移。

终态任务记录在创建新任务时按七天阈值清理，不影响已保存的聊天消息。机会记录不使用同一清理策略。删除账户时同时清理其任务与机会记录。

已用人工 v0.2.0 数据验证正向升级：资料、对话与记忆保持原样，新表自动建立且功能默认关闭。部署时必须使用原数据卷；推荐保留原 Compose 项目名，更名时需显式映射原卷。

直接回退到纯上游 v0.2.0 并不是完整的数据回退。旧版的账户删除流程不会清理本模块的三张表；保留启用记录时会触发 `visit_outreach_on` 的外键错误，任务表中的正文也不能依赖旧版替你删除。可恢复升级前数据库（不含升级后的新增记录），或停止后端并完整备份当前库，在副本上清理 `visit_outreach_on`、`dev2_night_tasks`、`dev2_night_opportunities` 后验证旧版兼容性；不能只替换镜像。原有账户、对话、记忆、亲密度和已正式保存消息所在的 `reach_outs` 表不应删除。

具体备份与回退步骤见根目录 [README 的「存在的问题：升级与回退」](../../../../README.md#存在的问题升级与回退)。已验证直接回退的外键问题；三表卸载迁移工具尚未提供或验证，不应将此方案当作已验收的自动回退功能。

## 运行与费用边界

当前任务管理按单个后端进程设计，正式 Dockerfile 默认也是单进程启动。不支持将同一数据库同时交给多个后端 worker 或副本：每个进程的启动恢复会把活动任务标为中断，内存中的忙碌状态也不共享。

前端连续停留是体验规则，不是服务端防刷凭据。直接请求 API 可以略过这段等待，后端仍会检查身份、资格、未回应状态以及任务复用。今晚模式按设计不使用自然模式的每晚准备上限；搭话使用部署者的模型密钥，费用不计入普通对话的每小时次数。公开服务需要另行考虑调用预算，不能把 5–8 秒等待当作费用保护。
